# Security Policy

Mnemarr stores sensitive material: full conversations with AI assistants and notes about your work. We take security reports seriously.

## Reporting a vulnerability

**Do not open a public issue.** Use GitHub's [private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability) on this repository ("Security" tab, then "Report a vulnerability").

Please include the affected version, reproduction steps and the impact you observed. We aim to acknowledge reports within 7 days.

## Supported versions

Until 1.0, only the latest release receives security fixes.

## Security model (summary)

Mnemarr is at the foundation stage: it reads folders of Markdown notes, searches them, and writes notes in the sources that are declared read-write (through the interface, the REST API and an MCP server). It **does authenticate**: every call but the probes, the interface's shell and the sign-in call needs a session or a key.

**True today**

- **Access is closed by default** ([ADR 0016](docs/adr/0016-accounts-roles-and-service-accounts.md)). Anonymous is `/health/live`, `/health/ready`, the static shell of the interface and the sign-in call; the system status and the OpenAPI document need a sign-in. A fallback policy requires a sign-in on any endpoint that declares nothing, and a test lists the anonymous ones. There is no "trusted network" mode.
- **People** sign in with a name and a password (hashed with PBKDF2, 12 characters at least, five failures lock the name for up to fifteen minutes) and get an `HttpOnly`, `SameSite=Strict`, `Secure` session cookie (named with the `__Host-` prefix) backed by a session on the server, of which only a hash is kept (signing out, a new password, disabling the account and a lifetime limit end it, wherever the cookie was copied); the sign-in call is limited in concurrency and in size; a write that does not carry an API key needs a custom request header. **Services and assistants** have service accounts, and only they have API keys (a person has none): 256 random bits, shown once, stored hashed, revocable, optionally expiring and limited to some sources, and never above their account's role.
- **Roles** are sets of permissions from a closed list in code (`Admin`, `Operator`, `Reader`, `Assistant`, `Collector`, `Monitor`). Permissions are read from the database on every request: disabling an account, changing its role or revoking a key applies at once. The last enabled administrator cannot be removed.
- **Sign-ins, their failures, changes to accounts and keys, and refused keys are audited** (what anyone can provoke is sampled, and the log has a retention); the audit log never holds a secret.
- **If the only administrator cannot sign in**, set `MNEMARR__AUTH__RESETPASSWORDUSER` and `MNEMARR__AUTH__RESETPASSWORDFILE` for one start, then remove them ([configuration](docs/configuration.md)). `/health/ready` reports "degraded" while there is no account at all.
- **A source is a folder the operator allowed.** Declaring one through the API is a request to read a folder: its path must be inside `Sources:Roots` (by default the `sources` folder of the data folder), and a relative path, a missing folder or a link (anywhere between the root and the folder) is refused, again before every scan, and before each file is read the file and every folder above it are checked for a link. The check and the read are two steps, so a folder swapped for a link in between is a known, narrowed window (a hard link to a file elsewhere on the same disk is not detected either); a Git source is cloned by the engine, which controls the checkout (see the next point). A special file named like a note or an image (a named pipe) in a vault a person can write to can block the read of it: vaults are the operator's own folders, and a read that cannot be interrupted is a known limit. A key limited to some sources sees the folder of each of its own sources (it may change their mode, so it has to know what they are), not the list of the folders of the host. A key limited to some sources can change the mode of its sources, not their name or folder, and cannot declare or forget one: otherwise it could repoint a source at another folder, or make its own scope match nothing. Forgetting a source never touches its files; a search shows only the sources the caller may touch.
- **A Git source is a request to connect and to send a secret, and is bounded** ([ADR 0022](docs/adr/0022-git-sources-are-cloned-and-pulled-in-process-over-https.md)). The address is `https` with a host and a path and nothing else (no user name, password, query or fragment: a secret does not go in an address); the operator names the hosts (`Git:Hosts`; **empty means none**, so no Git source is accepted until they do, and the list is read again at every sync) and the credentials, each **bound to one host** (and the address uses the https port, so a token cannot be sent to another service of that host), checked when a source is declared and again at every sync; a checkout cannot be placed inside another source's folder (what an outside repository brings must not appear as notes of the memory vault); a source names a credential and never holds a token, which is never stored in the database, exported, returned, audited or logged, and is offered once and not retried. Cloning is done in the process by libgit2: no `git` binary, no shell, no hook or configured command can run. Mnemarr never clones over a folder that has files, never merges, never forces, and leaves a checkout that diverged or has changes as it is. A failure is a code with fixed words, never a message from the host. Known limits: HTTPS and a token only (no SSH); one sync of one source is given up after `Git:SyncTimeoutSeconds` (and when Mnemarr stops); redirects are followed by libgit2 but the token is offered only to the declared address; a repository is cloned whole, so a very large one costs disk and time; a host the operator allowed can be an internal address of their own network, which is theirs to decide.
- **Writing notes is bounded** ([ADR 0023](docs/adr/0023-notes-are-written-through-the-api-committed-to-git-and-offered-over-mcp.md)). It needs `notes.write` (`Admin`, `Operator`, `Assistant`), a source declared read-write and, for a key, that source in its scope (another is absent). A path is relative, plain, not hidden, ends in `.md`, stays inside the source and never goes through a link; a note is written whole and atomically, at most 2 MB, with no NUL; a change names the version it read and is refused if the note moved on; every write is audited under the account's name and never with the text. A removed note is kept (Git history, or the hidden trash folder of the source). A Git source is committed per change with only the paths touched, as the account, and pushed as a fast-forward: the host and the credential are checked at every push like at every sync. **The MCP server** is the API again (same permissions, same scopes, same checks): a tool is offered only to a role that holds its permission, and **the writing tools are off unless the operator sets `Mcp:WriteTools` in the environment**, which no call can change (it governs MCP only: a key whose role holds `notes.write` can also write through the REST API, so give an assistant that must only read the `Reader` role). A note that an assistant writes is text like any other and is read as untrusted by the reader. Known limits: an assistant with write rights can fill a read-write source with notes (the audit log and Git history are how it is undone); a rename rewrites links only in the notes of the same source; the commit address is a setting, not a person; secrets are not masked in notes yet (do not write one, and Git history keeps what a removal took out); `/mcp` is held to the cross-site rules of the API (ADR 0016).
- **Conversations are sensitive, and are collected under bounds** ([ADR 0024](docs/adr/0024-conversations-are-collected-by-position-masked-twice-and-written-as-notes.md), [docs/collector.md](docs/collector.md)). **Conversations are read only by the roles that hold `conversations.read` (`Admin`, `Assistant`)**: for the others the source is as absent as one that does not exist, in the tree, the reader, the search and MCP, and that, more than masking, is what protects them. The ingest endpoint takes only a key of the `Collector` role (`ingest.write`, nothing else: such a key reads no note and no list), and is held to the cross-site rules of the API. A batch is at most 1000 lines of 2 MB in 8 MB (the cost of a batch does not grow with the conversation: new turns are added to the end of the note); the collector refuses a server address that is not `https://` (except this machine) and follows no redirect, so that its key goes only where it was sent; the machine and the session are plain names (letters, digits, dots, hyphens, underscores), so that no name can leave its folder. The server never trusts the collector's masking: it masks again, with the same rules, before anything is stored or indexed, and refuses a line it cannot check (a rule that takes too long). The raw lines are kept masked, compressed, in the data folder, outside Git and outside any source; the notes made of them are in a source that nobody can write by hand, rendered in a code fence so that a conversation cannot make links, tags or headings of its own. Upgrading widens what an existing unscoped `Assistant` key can read (it now holds `conversations.read`): limit such keys to sources. Known limits: masking is by patterns and will miss a secret that looks like nothing (the conversation is the operator's data: it is part of the backup, and a retention policy is not built); a collector key can add false conversations, and until enrolment binds a key to its machine it can write under any machine name (it is revocable; the audit log does not record each batch, and the list of machines says which sent what and when); a machine that is silent shows only by the age of its last conversation until the heartbeat is built. Designed, not built ([ADR 0025](docs/adr/0025-the-collector-is-a-service-per-machine-enrolled-by-a-code-and-configured-from-the-server.md)): a collector is enrolled by a one-time code that a person approves (15 minutes, once, one machine), configured from the server among readers it knows and never given a path to read, and run as the user whose files it reads.
- **A configuration document is input from outside** and is read strictly: at most 256 KB, one document, a bounded depth, no anchors, aliases or tags, and an unknown key is an error. A document with an error changes nothing. A key limited to some sources can neither export nor apply one, a configuration file is the only document when one is given, and what a document owns cannot be changed by hand. Secrets never go in a document ([ADR 0020](docs/adr/0020-configuration-as-code.md)).
- **A note is untrusted text.** The reader renders Markdown without raw HTML, keeps only `http`, `https`, `mailto` and relative links (a web link opens with `noopener noreferrer nofollow`), shows images only from the note's own source through the authenticated API (a short list of formats, never SVG, at most 10 MB, `nosniff`), and reads only notes the index knows, inside their source, never through a link. Mermaid diagrams in notes are drawn in the library's strict mode and shown as images (an image cannot run a script; while one is drawn, Mermaid works in a scratch element of the page, and what keeps a hostile label from running then is the Content-Security-Policy); the Content-Security-Policy therefore allows inline styles (`style-src 'self' 'unsafe-inline'`), and still no inline script and no `eval`, which must never be allowed. A source out of the scope of a key is absent from the tree, the tags, the links and the backlinks.
- **The first administrator** comes from `MNEMARR__AUTH__ADMINUSER` and a password read from the file named by `MNEMARR__AUTH__ADMINPASSWORDFILE`, only while there is no account. Mount that file as a secret; never put the password in an environment variable.
- Every response, errors included, carries conservative security headers and a Content-Security-Policy that lets scripts, fonts, connections and frames come from the application only (inline styles are allowed, for diagrams); an error never shows its cause.
- The image runs as a non-root user, with no shell; the deployment examples run it with a read-only root filesystem and no capability.
- The CI scans for secrets and vulnerable dependencies, and the code is analysed by CodeQL and SonarQube.

**The target model** (decided, not implemented: nothing below holds yet, except what is stated above)

- Nothing leaves the host unless the operator configures it; any external model or embeddings API is opt-in.
- Secrets are never stored in memories nor returned by the API: they are masked before they leave the machine that holds the conversation, and checked again on the server.
- A collector agent holds an ingest-only credential (the `Collector` role), one per machine and **bound to that machine's name**, revocable: a compromised agent can add conversations as its own machine and as no other, and it cannot read any memory. A machine joins with a one-time code (12 characters, hashed, single use, 15 minutes from the approval of a person who manages the collectors); the exchange is anonymous and, for the whole server, limited to ten wrong codes a minute. An assistant may ask for a machine to be added, but the code is of no use until a person approves the request ([ADR 0027](docs/adr/0027-machines-join-with-a-code-hold-a-key-bound-to-their-name-and-say-they-are-alive.md)).

The threat model is in the [specification](docs/SPEC.md), §6.
