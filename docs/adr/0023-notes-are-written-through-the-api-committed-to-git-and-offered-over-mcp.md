# 0023 — Notes are written through the API, committed to Git, and offered to assistants over MCP

- **Status**: accepted
- **Date**: 2026-11-04
- **Spec**: D-43 (implements the write side of [ADR 0015](0015-sources-are-read-write-capable.md) and F-MCP-01; builds on D-37, D-39 and D-42)

## Context

Mnemarr could read: sources, an index, a reader, Git checkouts that are kept up to date. A memory that cannot be written is not a memory, and the people and assistants who use it need one way in that respects the same permissions whoever comes: the interface, the REST API, an assistant over MCP.

## Decision

1. **One writer, used by every way in.** `NoteWriter` creates, changes, appends to, moves and removes a note. The REST API (`POST/PUT/DELETE /api/v1/notes/{source}/{path}`, `POST …/rename`) and the MCP tools are thin layers over it: an assistant can do nothing there that the API would refuse. It needs `notes.write` (`Admin`, `Operator` and `Assistant` hold it, `Reader`, `Collector` and `Monitor` do not), and a key limited to some sources writes only in those (another source is as absent as one that does not exist).
2. **The mode of a source is the switch** (D-35): a source declared read-only refuses every write (403), read-write accepts them. Nothing is written outside a source's folder: the path is relative, made of plain names (none hidden), ends in `.md`, stays inside the folder and never goes through a link.
3. **A note is written whole and at once.** Written beside the note and moved into place, so that a reader sees the old text or the new one, never half of one. A text is at most 2 MB and holds no NUL character. The whole file is the unit (the front matter included): the editor changes the file as it is.
4. **A change says which note it changes.** The version of a note is the SHA-256 of its file. A change (`PUT`, `update_note`) sends the version that was read and is refused (409) when the note is no longer that one: nothing is overwritten, and what the person typed stays on the screen. An append and a creation need no version (a creation is refused when the note exists).
5. **The index follows at once, and nothing reads a folder that is changing.** After a write the note is read into the index in the same call, and every change holds the lock of the source, shared with scans and syncs (a change waits ten seconds for it, then answers 429).
6. **Moving a note keeps the vault together.** A rename rewrites the links that lead to the note in the notes **of the same source** (wikilinks, in the style they were written: a name stays a name, a path stays a path, a relative path stays relative, with their heading and their text; ordinary Markdown links, with their heading and title), and the relative links of the moved note itself so that they still lead where they led. What is in code is left alone, and the line endings and the front matter are kept. Links in notes of **other** sources are not changed (the source may be read-only or not the caller's) and the answer counts them. Ordinary Markdown links to notes are now links like wikilinks (they give backlinks), and a link to a heading (`[[note#Heading]]`, `note.md#heading`) leads to it (the headings the interface draws carry the slug of their text).
7. **Removing keeps what was removed.** A note of a Git source is deleted and committed (its history keeps it). A note of a plain folder is moved into the hidden `.mnemarr-trash` folder of the source, which nothing reads. Mnemarr never destroys a note.
8. **A Git source is written by a commit pushed to its remote.** Each change is one commit, authored by the account that made it (`Git:CommitEmail`, default `mnemarr@localhost`, is the address: it is not a person's mailbox), that holds **only the paths the change touched** (what else is in the folder is not that commit's business), pushed as a fast-forward of the configured branch: never forced. A push that fails (the host is down, the branch is protected, the token cannot write) does not undo the change: the note is written and committed, the answer says it was not pushed and why (`git.error`, a fixed code), the source shows the code and readiness is degraded, and the next sync pushes what is waiting. Before it writes, Mnemarr brings the checkout up to date (a fast-forward, inside the lock of the source), so that the push that follows is a fast-forward too. A checkout that has diverged refuses the write (409, `diverged`) and is left as it is: nothing is piled on a branch that cannot be pushed, and the operator brings it back in line by hand. A host that cannot be reached does not refuse the write: it is committed and a later sync pushes it. A push, like a sync, gives up after `Git:SyncTimeoutSeconds`.
9. **The MCP server** (`POST /mcp`) speaks the Model Context Protocol over HTTP, one JSON-RPC message per request, answered at once as JSON (the "Streamable HTTP" transport without a stream: the server never starts a message of its own, keeps no session, and `GET` answers 405). An assistant connects with the API key of a service account. Tools: `list_sources`, `search`, `list_notes`, `read_note`, `list_tags`, and the writing tools `create_note`, `update_note`, `append_to_note`, `rename_note`, `delete_note`. A tool is offered to a caller only if their role holds its permission. **The writing tools are off by default and a setting of the environment** (`Mcp:WriteTools`), not of the database or of the API: the door that decides whether an assistant may write over MCP must not be one the assistant can open. That switch governs MCP only: a key whose role holds `notes.write` can also call the REST API, so the role of the account is the real control, and an operator who wants an assistant to read only gives its account the `Reader` role. A refusal of a tool (a stale version, a read-only source) is a tool error the assistant can read, not a failure of the protocol. `/mcp` is held to the rules of `/api`: a request that rides on a session cookie and not on a key must carry the header of ADR 0016, and the body must be `application/json`. The server is written by hand (about 300 lines, no new dependency, the maintainer decides on those): the official C# SDK was the alternative. It is the right choice while the server is stateless and offers tools only; resources, prompts or streaming are the trigger to move to the SDK. The list of protocol versions it accepts is in the code and is updated by hand. Every write is audited under the account's name, never with the text of the note.
10. **The interface** edits the whole text of a note with a preview drawn by the server (links resolved as they will be once saved), creates a note in a source open for writing, moves it (the links follow), and removes it after a second press. It shows what became of the commit when the source is a Git repository.

## Consequences

- A person, an assistant over MCP and a script write through the same checks; the audit log says who did what (`note.created`, `note.updated`, `note.renamed`, `note.removed`).
- A write to a source that a sync or a scan is working on waits for it; a long clone can make a write answer 429, which the caller retries.
- Links in other sources are not rewritten by a rename (the count says how many were left). A rename in a Git source commits every note it touched in one commit.
- Two people editing the same note do not overwrite one another: the second is told.
- **The memory vault has a second author: people.** D-14 gave it to the AI alone, and Q-34 asked whether assistants and people may write it. The answer, written here: a person who holds `notes.write` may correct a memory note when the source is declared read-write (the default is read-only, and the interface says why a note cannot be edited); an assistant over MCP may do the same only when the operator turns the writing tools on. Consolidation (D-14) stays the author of structure, and every correction is audited and, in Git, one commit under the account's name. This supersedes the last sentence of D-14 and the "does not edit" of D-37.
- **Application documentation is never written here** (its kind refuses, whatever the mode of its source): it changes by pull request in the repository of the application.
- **No masking of secrets yet.** D-10 plans it for what collectors send; a note written by a person or an assistant is stored, committed and pushed as it is, and Git history keeps what a removal took out. Until masking exists (Q-27), leave the MCP writing tools off for assistants that may hold secrets, and never write a secret in a note.
- Operators change the notes of a vault from the interface, which D-18 said only configures the brain: D-37 already made the reader, and this makes it an editor (ADR 0017 lists what the reader may not do: write and run are now allowed for people who hold `notes.write`).
- Not here: merging a diverged checkout, a pull request instead of a push, the history of a note in the interface, notes written by a collector or a consolidation job (they use this writer when they come).
