# 0016 — Accounts, permission-based roles and service accounts

- **Status**: accepted
- **Date**: 2026-11-03
- **Spec**: D-36 (closes Q-14 and Q-25; applies the rule of section 6 on anonymous endpoints; refines D-27, whose per-user keys become keys of service accounts)

## Context

The specification requires authentication "no later than the first endpoint that exposes memory content or settings", and Mnemarr authenticates every call itself (D-27). The maintainer wants people to sign in to the interface with rights that differ (a user who may only read the notes, not configure anything) and **service accounts** with keys for the agents and assistants that read or write through the API and the MCP server. Portarr solved the same problem (its ADR 0009); this follows it, for what Mnemarr needs.

## Decision

1. **One kind of principal for every way in: an account.** An account is a **user** (a person: name and password) or a **service account** (an agent or an assistant: no password, keys only). The cookie of a session, an API key and, later, an OAuth token all produce the same principal.
2. **Local accounts with a cookie session** for people: forms login, passwords hashed with ASP.NET Core's `PasswordHasher` (PBKDF2), a minimum length, a lockout after repeated failures (five within fifteen minutes lock the name, whether it exists or not, until the failures age out), the same answer for an unknown name and a wrong password. The cookie is `HttpOnly`, `SameSite=Strict` and `Secure` by default, and named with the `__Host-` prefix then, so that a sibling host cannot set one. The sign-in call is limited to four checks at the same time (each costs a password hash) and to a small body; a wrong current password on a password change counts like a failed sign-in. A custom request header is required on a write sent with the cookie (CSRF; the path is compared without regard to case, as the routing is). **Sessions live on the server**: the cookie carries the id of a session row, so signing out, a password change (the other sessions only, when a person changes their own; all of them when an administrator sets it) and the end of an absolute lifetime (30 days by default, however much it is used) end a session wherever its cookie was copied. The cookie also slides, with an idle limit (12 hours by default). The server keeps only a hash of the session id, so a copy of the database and of the key ring together is not a cookie either. Disabling an account ends its sessions as well.
3. **A role is a named set of permissions, and the permissions are a closed list in code.** There is one authorization policy per permission, declared on each endpoint, and a **fallback policy that requires a sign-in everywhere else**, so a forgotten attribute fails closed. The built-in roles are defined in code, not stored:
   - `Admin`: everything (accounts included);
   - `Operator`: read notes, search, manage sources, read the system status (it does not write notes: that is the role of an assistant; a person who must write notes in the interface will get a role for it with that feature);
   - `Reader`: read notes and search, nothing else;
   - `Assistant` (service accounts): read and write notes, search;
   - `Collector` (service accounts): send conversations, nothing else.
4. **Permissions are read from the database on every request**, not copied into the cookie or a token: disabling an account, changing its role or revoking a key applies at once. The last enabled `Admin` can be neither deleted, disabled nor demoted.
5. **API keys** belong to a **service account** (a person has no key: a bearer credential that skips the lockout, the CSRF header and the cookie's protections, on an administrator, could create administrators), are 256 random bits shown once, stored only as a hash, revocable, optionally expiring, with the date of their last use. A key never exceeds its account's role: its permissions are the account's, **narrowed by its scope**, an optional list of the sources it may touch (section 6 of the specification). A key scope lists at least one source (an empty list would read as "all of them" somewhere and "none" elsewhere, so it is refused). Sent as `Authorization: Bearer` (the scheme in any case) or `X-Api-Key`. The verb of an assistant (read only, or read and write) is the role of its account: a `Reader` service account for one that must only read.
6. **The first administrator** is created at start from `MNEMARR__AUTH__ADMINUSER` and a password read from the file named by `MNEMARR__AUTH__ADMINPASSWORDFILE`, only when there is no account yet. There is no default account. **Break-glass**: while `MNEMARR__AUTH__RESETPASSWORDUSER` and `MNEMARR__AUTH__RESETPASSWORDFILE` are both set, that account gets the password in the file at each start, is enabled, and loses its lockout and its sessions; both are removed once used. `/health/ready` says "degraded" while there is no account at all.
7. **Anonymous is a short list**: `/health/live`, `/health/ready`, the static shell of the interface and the sign-in call. The status of the system and the OpenAPI document need a sign-in. There is **no "trusted network" mode**.
8. **Access is audited**: sign-ins (and their failures), changes to accounts, roles and keys, and refused keys are appended to an audit log the administrator reads; the use of a key is recorded as its date of last use. Events that anyone without a credential can provoke are bounded: failed sign-ins on a name that exists by the lockout (five per name per fifteen minutes), refused keys and locked names by a sample (once a minute per key, sixty a minute for each kind of event); the whole log keeps 90 days by default. Reads and writes of notes join the log with the verticals that bring them.
9. **OAuth for agents is a later step** (the client-credentials grant for service accounts, which the MCP specification uses for remote servers). A new scheme only has to produce the same principal.

## Consequences

- Every endpoint has a permission; the matrix role × endpoint is an integration test, and a new endpoint with no policy is a sign-in-only endpoint, visible in review.
- Permissions per source for people (a user who only sees one source) are not in this step: roles are global for a user, and a key can be scoped to sources. The model leaves room for it.
- One Mnemarr instance per database: the lockout counters live in memory (bounded: a name is limited in length, and a locked name is never forgotten to make room, so garbage names can neither grow them nor lift a lockout). A lockout is per name: whoever knows an administrator's name can lock it for fifteen minutes (a person's own break-glass is above). A per-address limit belongs to the ingest vertical, with the proxy's forwarded headers.
- The account roles for sources (a person who sees only one source) will need a join table instead of a global role; sessions and keys do not depend on it.
- The architecture test that would keep `Mnemarr.Core` free of `Microsoft.Extensions.Identity.Core` beyond the password hasher is not written: Core takes that package for `PasswordHasher` on purpose (one dependency, no schema), and the hasher is behind `IPasswordHasher<Account>`.
- The ingest vertical reuses the `Collector` role and the key scoping: **one service account per machine**, each with its own keys, so that revoking a machine is disabling an account. The MCP server reuses the keys.
- **The scope of a key must be impossible to skip.** Permissions fail closed (the fallback policy); the limit to sources is carried by claims and read through one accessor (`CanAccessSource`) that fails closed. The sources, notes and MCP verticals take the source as a parameter of their queries and ask that accessor, and the role × endpoint matrix grows scoped keys with them.
- **The write check of the CSRF header covers `/api`.** An endpoint outside it that a cookie could write to (none today; MCP is called with a key) must join the check or carry its own.
- **This vertical introduces the storage layer** (Q-22) in its simplest form: ADO.NET over `Microsoft.Data.Sqlite`, a schema in numbered steps kept in `PRAGMA user_version`, WAL and a connection per call. Accounts are step 1; the sources vertical becomes step 2 of the same `Schema` when it is rebased. Q-22 stays open for what it asks beyond that (the writer shared with ingestion and embedding, the `sqlite-vec` connection).
- `SessionHours`, `SessionMaxDays` and `AuditRetentionDays` are environment settings until the settings API (D-18) exists, and move there; the bootstrap settings (the first administrator, the password files, the cookie mode) stay in the environment.

## Alternatives considered

- **Full ASP.NET Identity**: brings its own schema, UI assumptions and migrations, for features (e-mail confirmation, external logins, two-factor) that are not wanted yet.
- **Fixed roles as an enum**: simpler, but permissions as the unit cost little more and a role never has to be guessed.
- **Permissions in the cookie or a token**: stale until it expires; a disabled account or a revoked key would keep working.
- **A "trusted network" or "disabled for local addresses" mode**: the day a port is published or a proxy is misconfigured, it opens the memory. Single sign-on in front of the interface stays a layer, not a replacement (D-27).
