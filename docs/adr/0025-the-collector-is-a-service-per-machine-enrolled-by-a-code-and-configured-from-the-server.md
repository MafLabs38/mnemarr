# 0025 — The collector is a service on each machine, enrolled by a code, and configured from the server

- **Status**: accepted
- **Date**: 2026-11-05
- **Spec**: D-45; refines D-08, D-09, D-10, D-13; refines [0005](0005-collector-agent.md) (installation, configuration, silence, readers) and [0024](0024-conversations-are-collected-by-position-masked-twice-and-written-as-notes.md) (layout, who reads)

## Context

[0005](0005-collector-agent.md) decided that a small agent runs on every machine where an assistant runs, and [0024](0024-conversations-are-collected-by-position-masked-twice-and-written-as-notes.md) built the first slice of the chain. Three things were left open and have to be decided before the collector grows: how it is installed, configured and watched on machines that are not alike, and which assistants it reads.

- **Machines are not alike.** Some are servers or virtual machines that run all the time; some are physical workstations (a Windows development PC) that sleep, are switched off at night, and must never be kept awake or slowed down by Mnemarr. An absent machine is normal for the second kind, and an error for the first.
- **A workstation cannot be installed by infrastructure as code.** Somebody has to install the collector by hand on it, safely, without copying a secret around.
- **There is more than one assistant**: Claude Code, Codex CLI, GitHub Copilot (in VS Code, and its CLI), Gemini CLI. Their files do not look alike ([the formats](../conversation-formats.md)).

## Decision

1. **The collector is a service that runs as the user whose files it reads.** Conversation files are in the profile of the person who held them, so it runs as that user, never as root or `SYSTEM`. Two forms: **a container** for servers and virtual machines (Docker or Compose, with the folders of conversations mounted read-only), and **a per-user service** for workstations (a scheduled task at logon on Windows, a systemd user unit on Linux, launchd on macOS: no administrator rights). The program installs itself: `mnemarr-collector install`, `uninstall`, `status`.
2. **Two ways to install it on a workstation.** *From a release*: download the binary of the GitHub release (Windows, Linux, macOS; a checksums file, verified by the install script; signing and an attestation of provenance come with the release pipeline), then `enroll` and `install`. *Guided from Mnemarr over MCP*: an assistant on that machine (in VS Code, say) calls an administration tool that opens an **enrolment request** for the machine; Mnemarr answers with the exact commands and a one-time code; the code works only after a person who holds `collectors.manage` has approved the request in the interface. Mnemarr executes nothing on the machine: the person runs the commands, with the usual approval of their assistant. Winget and a registry entry are possible later, and change nothing here.
3. **Enrolment, not a copied key.** The one-time code is short-lived (15 minutes), used once, and bound to a machine name. `mnemarr-collector enroll --server URL --code CODE` exchanges it for an **ingest key**, shown once and written to a file only its user can read. The server creates (or reuses) the service account of the machine, with the role `Collector`. A machine is revoked by revoking its key. A code or a key is never in a configuration document or in Git.
4. **The server says what to collect; the machine says where.** The configuration of the collectors lives on the server, in one model reached four ways, like the sources (ADR 0020): a `collectors:` section of the configuration document (machine, kind, readers that are on), the REST API, the interface, and an MCP administration tool. A collector reads its own entry at the start of each pass (`GET /api/v1/ingest/config`, with its key), so a change applies without touching the machine. On the machine there remains only a small bootstrap file: the address of Mnemarr, the key file, the name of the machine, and, when the usual place is not the right one, the folder of a reader. **The server chooses among the readers the collector knows and never names a path**: a server that was compromised, or a configuration that was edited, must not be able to make a collector send `~/.ssh`.
5. **A machine that sleeps is not a machine in error.** The collector never prevents the machine from sleeping, never wakes it, holds no wake lock or timer, and runs at a low priority. When the machine sleeps or is off nothing is collected and nothing is wrong; at wake it resumes from its positions (a jump of the clock is ordinary). Each pass it sends a **heartbeat** (its version, when the pass ended, what is left to send, the error of a reader). Each machine has a kind: **`always-on`** (a server) or **`intermittent`** (a workstation). Silence beyond a threshold (30 minutes by default, a setting) is an alert only for `always-on`; an `intermittent` machine shows when it was last seen and never raises one. The health page says which it is: online, asleep or off (intermittent), silent (always-on), refused (its key was revoked), failing (a reader reports an error).
6. **Readers, behind one contract.** The collector has a closed list of readers; each knows where the files of one assistant are, by operating system, and turns them into **lines**, the unit of position (ADR 0024). Two families: files that only grow, one JSON object per line (Claude Code, Codex CLI, Copilot CLI), which the reader sends as they are; and JSON documents that are rewritten (Gemini CLI, Copilot in VS Code), which the reader flattens into one line per message, in a stable order, sending only the messages past the position. A message that was rewritten after it was sent is not sent again (a known limit). The server has one parser per `format` that turns lines into turns. Claude Code is built; the others come next and are checked against real files before they are called done (Copilot can be tried by the maintainer; Codex and Gemini have no account at hand, so their readers start from the documented formats and are marked untested). A reader skips what it does not understand.
7. **The conversations are filed by machine.** `<machine>/<application>/<day>-<session>.md` in the Conversations source (replaces the layout of 0024), so that the first folder, the topic of a search, is the machine, and the application is a tag.
8. **Who reads conversations.** The new permission `conversations.read` is held by `Admin` and by `Assistant`; `Reader`, `Operator`, `Monitor` and `Collector` do not hold it, and for them the Conversations source is as absent as one that does not exist, in the tree, the search, the reader and MCP. A key of an assistant is given on purpose by an administrator and can be limited to sources. Masking stays by patterns and is not pursued further: the protection that counts is who can read.
9. **Titles.** A conversation is titled from the first sentence that says something (not a greeting, a code block or an address). A summary written by a model is an option of the consolidation (it needs a call to a model, so it is opt-in, and costs a little for each conversation).
10. **Compatibility.** A collector sends its version; the ingest contract only grows within `v1`, so older collectors keep working; below a minimum version the server answers with a problem that says to update (closes Q-28 for now).

## Consequences

- A workstation is installed by a person in a few minutes, with no secret to copy; a server by a Compose file.
- An intermittent machine can be off for days without alerting anyone; an always-on machine that goes quiet is noticed.
- Adding an assistant is adding a reader and a parser, not a change of architecture.
- The collector grows from a loop with flags into a small service: configuration fetched from the server, heartbeat, an installer, release binaries for three systems (a build matrix, and a Windows machine to try it on).
- Not here: the readers other than Claude Code, the second key per machine for reading memory at the start of a session (Q-26: the enrolment will issue it on request), retention, a collector that reads on behalf of several users of a machine.
